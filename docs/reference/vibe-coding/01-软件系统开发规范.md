# Vibe Coding 开发手册（v0.5）

软件项目需要清楚的业务目标、可理解的代码结构和可重复的验收。人负责确定目标、划分职责和接受结果，AI 根据明确的约束完成实现、检查和修订。前端展示状态，后端执行业务规则，数据库保存事实；微服务边界、强类型和目录约束使这些部分能够持续修改。

“必须”表示项目需要遵守的边界；“应”表示默认采用、调整时需要记录理由的做法；“可”表示按实际需要选用。项目采用的技术、目录、构建命令和服务清单必须填写到自己的 `AGENTS.md`。具体实现可参考 [Scala + React 架构方案](02-架构方案与实现对照.md)。

当前版本：v0.5，2026年10月28日。主要依据课程 `99_HTML笔记` V1.8；微服务部署、服务卡、目录依赖和验收条目属于工程补充，具体来源见文末。

## 一、Vibe Coding：先决定做什么，再检查是否做到了

### 基本思路

Vibe Coding 是人与 AI 共同开发软件的工作方式。项目负责人说清用户需要完成的任务、系统必须保持的业务事实以及结果怎样验收；AI 将这些要求转成代码和检查。随着功能增长，同一个概念在页面、接口和数据库之间必须保持含义一致。

核心业务计算应有明确的输入和输出。例如“当前借阅数是否达到上限”可以由两个数字计算得到；读取当前借阅数、保存新记录属于与外部世界交互的操作。这些操作集中在容易找到的边界，错误才有可追查的位置。

### 建议的语言与技术组合

面向本课程的中小型业务系统，建议后端采用 **Scala 3**，前端采用 **TypeScript + React**，数据库采用 **PostgreSQL**。后端用 **Cats Effect** 组织外部操作，前端用 **Vite** 管理开发和构建，样式沿用项目选定的 Tailwind 或现有体系。这个组合适合包含登录、列表、表单、审批或业务记录等流程，并需要持续修改的项目。

| 部分 | 建议选择 | 承担的任务与选择理由 |
| --- | --- | --- |
| 后端语言 | Scala 3 | 用 `case class`、`enum` 和类型化函数表达业务对象、状态与结果；类型检查帮助发现部分连接错误 |
| 外部操作 | Cats Effect 的 `IO` | 明确数据库、网络和文件操作的组合、执行及资源生命周期 |
| 前端语言与界面 | TypeScript + React | 用类型描述输入和状态，用组件声明不同状态下的页面 |
| 前端构建 | Vite | 组织本地开发和前端资源构建；页面职责仍由业务目录决定 |
| 数据语言与数据库 | SQL + PostgreSQL | 表达查询、关系与约束，用本地事务维护需要共同提交的业务事实 |
| 整体组织 | 模块化单体 | 一个后端应用内保持业务边界，集中完成初期构建、运行与排查 |

Scala 同时支持函数式和面向对象组织，适合将业务数据、类型与函数组合放在明确的模块中。团队需要具备维护 JVM、sbt、Scala 类型和效果计算的能力，AI 生成的实现仍须经过编译与业务验收。既有项目沿用已确认的语言与框架，新增功能保持其契约和目录一致；技术迁移需要单独说明收益与成本。

### 声明式：把目标、约束和状态写清楚

声明式编程强调希望得到的结果和必须满足的条件，由底层机制完成具体执行。对 AI 提出任务时，应把用户目标、输入、业务不变量、成功结果和失败反馈说清楚。例如：“为当前读者借阅选中的副本；成功后产生一条借阅记录；同一副本最多有一条有效借阅；副本不可借时返回明确原因。”这些声明可以继续分解成接口、类型、页面状态和验收条件。

在代码中，React 用当前状态声明界面，SQL 用条件声明需要的数据，集合的 `filter` 和 `map` 声明筛选与转换规则。声明式表达的清晰程度取决于目标和约束是否明确；数据库提交、网络调用等操作仍有具体顺序与执行责任。

### 函数式：用纯函数组织计算，用新值表达变化

函数式编程优先使用输入输出明确的函数、不可变数据和函数组合。纯函数的结果只依赖显式输入，相同输入得到相同输出，并保持外部状态不变。例如，已取得当前借阅数和额度后，可以直接计算剩余名额：

```scala
def remainingSlots(activeLoans: Int, limit: Int): Int =
  (limit - activeLoans).max(0)
```

当有效借阅数为2、上限为5时，结果为3。这个函数接收已校验的非负整数，负责一次确定的计算；当前借阅数由数据访问操作取得。借阅完成后，新的借阅记录和页面状态通过新值表达，数据库写入放在明确的操作边界。

建议采用“纯计算核心＋外部操作边界”：资格判断、额度计算、排序和格式转换优先写成纯函数，数据库、网络和文件操作通过 `IO` 等机制组织。函数可通过 `map`、`flatMap` 或 `for` 组合，但外部操作的失败处理和数据库事务仍须明确。复杂抽象应服务于实际业务表达与复用，团队需要能够解释每一步输入、输出和效果。

### 模块化：让业务职责与公开接口一致

模块化把系统分成职责清楚、可以分别理解和检查的部分。建议按照业务能力定义模块，将紧密相关的数据与规则放在一起，用公开契约连接模块。借书系统中，账户、书目和借阅流转分别承担身份、书目信息和借还规则；修改借阅期限时，相关变化应集中在借阅流转模块。

一个模块可以包含多个类型、函数、接口和数据访问方法。模块边界由业务职责与变化关系确定，部署边界根据独立发布和运行需求决定。初期可以由同一应用启动全部模块，逐步积累稳定的契约和验收。

| 基本原则 | 对 AI 的具体要求 | 可检查的结果 |
| --- | --- | --- |
| 声明式 | 写明目标、输入、约束、期望状态与失败结果 | 需求可以对应接口和验收场景 |
| 函数式 | 纯计算接收显式输入；数据变化优先返回新值 | 同一规则可独立调用，输入输出可单独核对 |
| 强类型 | 用独立类型表达身份、状态和结果 | 参数混用及遗漏分支可被检查，外部数据经过校验 |
| 模块化 | 按业务能力组织，高内聚、低耦合 | 普通规则变化集中于所属模块，跨模块调用有公开入口 |
| 效果边界 | 把数据库、网络和文件操作放到明确位置 | 执行顺序、资源释放、错误和事务有负责位置 |

### 工作约束

1. **写清任务**：说明用户、场景、输入、期望结果及第一版的范围。一个任务应能对应一次可验收的业务变化。
2. **先定业务概念**：列出对象、身份、状态和不变量。不变量是每次合法操作后都成立的条件，例如“一个馆藏副本同时最多存在一条有效借阅”。
3. **先画职责与数据流**：记录页面、后端业务服务、数据库、外部系统之间的调用方向和数据归属。
4. **分步实施**：复杂改动先列受影响的契约、服务、数据和页面；每步完成后核对构建和实际业务结果。
5. **要求验证证据**：记录执行过的命令、实际结果及待验证部分。界面显示成功、数据库写入成功和部署成功分别核实。
6. **控制工程成本**：增加架构层次、服务数量或基础设施时说明实际需求。针对推测性或极低概率的竞态、安全边界增加复杂度前，必须讲清具体问题、发生概率的依据和实现维护成本，并获得项目负责人明确同意。

**自己检查**：我能否说明一次操作经过哪些部分、谁改变数据、怎样确认结果？

## 二、前端：让页面跟着状态变化

### 建议架构：React 组件＋页面状态＋业务 API

建议以 **TypeScript + React + Vite 的单个前端应用**起步，按业务页面组织代码。页面入口组合业务区域，组件声明显示内容，页面 hook 协调状态与操作，API 调用器连接后端。这个结构适合以查询、填写、提交和结果反馈为主的业务界面。

```text
用户操作
  → 页面 hook → 业务 API → 统一 HTTP 请求 → 后端
后端响应
  → 响应校验 → 更新状态 → 派生计算 → React 组件显示
```

页面状态应放在最近的共同使用位置。筛选条件、当前选择和提交进度由页面维护；多个页面共同使用的身份等事实进入共享状态。服务端保存的借阅记录由请求结果更新到页面，需要刷新时通过已有查询接口取得当前事实。

建议采用以下默认安排，并与项目目录保持对应：

| 架构部分 | 建议落点 | 默认约束 |
| --- | --- | --- |
| 启动与路由 | `frontend/src/app/` | 连接页面入口，确定导航所需参数 |
| 页面与业务区域 | `pages/<Page>/index.tsx`、`components/` | 入口能看出主要区域，组件通过参数和回调协作 |
| 状态与交互 | 页面内 `hooks/`，必要的共享 Store | 核心状态有单一归属，更新入口可追踪 |
| 纯计算与类型 | 页面内 `functions/`、`objects/` | 排序、筛选和格式化由输入计算 |
| 业务请求 | `apis/<domain>/`、`objects/<domain>/` | 操作与后端契约对应，校验实际响应 |
| 通用传输与公共 UI | `system/api/`、`components/ui/` | 复用通信机制与稳定 UI；业务规则留在所属页面或后端 |

借书页面中的搜索框、书目列表和结果提示可作为组件，`useBookList` 协调选中副本、提交和反馈，`BorrowCopyAPI` 负责调用借阅接口。React 根据更新后的状态重新计算界面；授权、库存和借阅记录的最终判断由后端完成。

### 页面、状态与请求的分工

前端负责展示信息、接收输入和反馈进度。页面由当前状态推导出来：用户改变筛选条件，列表随之变化；后端返回借阅结果，按钮和借阅记录随之更新。核心状态是需要保存的事实，展示状态是由这些事实计算出的结果。

例如，分页列表保存 `books`、`selectedIndex` 和 `pageSize`，页码由索引计算。列表缩短后，选中位置需要回到有效范围。同一份列表同时保存在组件和全局 Store，会增加同步负担。每类状态必须确定一个更新入口。

| 位置 | 负责的内容 | 依赖边界 |
| --- | --- | --- |
| 页面入口 | 路由参数、主要业务区域和页面布局 | 组合本页组件与 hook |
| 页面组件 | 展示数据、接收点击和输入 | 通过参数和回调连接业务 |
| 页面 hook／store | 请求时机、核心状态及更新过程 | 调用业务 API；协调页面状态 |
| 纯函数 | 排序、筛选、分页、格式化 | 输入决定输出，便于独立验证 |
| 业务 API 调用器 | 请求参数、响应解码、业务结果 | 使用统一请求入口与契约类型 |
| 通用请求入口 | 服务地址、身份凭证、HTTP 错误 | 提供传输能力 |

### 异步状态怎样表达

有网络请求的页面至少需要区分初始、加载、就绪和失败。就绪状态中的空数组对应“暂无数据”；正在提交借阅对应提交中状态。失败提示需要给出可执行的动作，例如重新加载或重新选择副本。

React 的 Effect 用于连接网络、订阅等外部过程；筛选和格式化优先在计算中完成。共享 Store 对外提供读取快照、订阅变化和更新状态的入口。页面专用状态留在页面附近，登录身份等跨页面事实才进入全局状态。

### 工作约束

1. 每个页面必须列出可读取的信息、可提交的操作和各操作对应的后端接口。
2. 核心状态必须有明确归属；可推导的页码、过滤结果和格式化文字应通过计算获得。
3. UI 组件、业务计算和网络传输应分工清楚。业务 API 使用统一请求入口，页面通过约定的调用器访问后端。
4. 异步交互必须覆盖加载、就绪、空数据、失败和提交反馈；错误响应与正常业务拒绝分别呈现。
5. 复杂页面按可见业务区域拆分，入口文件应能看出主要区域。简单组件保持单文件，目录随真实职责建立。
6. 网络数据必须经过运行时校验后进入可信状态；字段名称、单位、空值和错误码与后端契约一致。
7. 前端权限提示用于交互体验；后端必须独立验证身份与当前操作权限。数据库凭证只由后端持有。

**自己检查**：点一次按钮后，哪份状态变化？请求失败时旧数据怎样呈现？用户能否理解下一步操作？

## 三、后端：按业务职责组织能力

### 建议架构：Scala 模块化单体＋分层业务服务

建议采用 **Scala 3 + Cats Effect + HTTP API 的模块化单体**：一个后端应用内包含多个按业务能力划分的服务，每个服务具有自己的公开操作、领域类型、路由和数据访问。初期使用一个构建和启动入口，服务间通过明确接口协作。这个结构适合业务边界仍在完善、需要频繁修改且由小团队维护的系统。

```text
前端 HTTP 请求
      ↓
统一传输与身份入口
      ↓
业务服务的 routes → api／plan → 所属 tables → 数据库
                       ↓
                领域类型与纯规则函数

Bootstrap 装配：accounts、catalog、circulation
system 提供：连接、配置、通用 HTTP 与资源管理
```

按业务域组织与服务内部的技术分层同时存在。`services/circulation/` 集中维护借阅能力，其 `routes/` 处理传输，`api/` 组织业务操作，`objects/` 表达业务含义，`tables/` 访问所属数据，`utils/` 放置确有复用的内部函数。一次借阅的主要步骤应能从操作入口读出来。

业务规则优先在纯函数中计算；`plan` 用 `IO` 组织读写和调用。数据库事务执行器为需要共同提交的步骤提供同一事务上下文。连接和配置由 `system/` 维护，顶层 `Bootstrap.scala` 负责装配服务。使用现有 HTTP 路由与数据库访问库时，沿用项目已验证的组合和命名方式。

当某个服务确有独立发布、扩容或团队维护需求时，可在稳定的公开契约基础上评估独立部署。拆分涉及网络调用、数据访问权限和事务范围的变化，需要同时记录收益、运行责任与维护成本。

### 一次请求经过哪些边界

后端接收请求，将外部数据转换成可信的业务输入，再执行业务规则并返回结果。路由、业务操作、数据访问各有职责，主要步骤应能从操作入口直接读出来。

```text
HTTP 请求
  → 路由：解码、识别身份、构造可信输入
  → 业务操作：检查权限与规则、组织执行步骤、确定事务边界
  → 数据访问：参数绑定、查询／写入、记录映射
  → 领域结果 → 响应编码 → HTTP 响应
```

领域对象表达系统中的业务含义，例如 `ReaderId`、`CopyId`、借阅状态。传输对象（DTO）表达 API 在网络上传递的字段。数据库记录表达表的存储结构。三者之间的转换要清楚，数据库增加内部列时，对外接口可以保持稳定。

外部调用、数据库读写和文件操作属于副作用。Scala 可以用 `IO[A]` 表达“执行后产生 A 的操作”，通过 `flatMap` 或 `for` 组合执行顺序；事务仍由数据库连接和事务管理器落实。

### API 必须约定什么

| 契约项目 | 借阅副本的例子 |
| --- | --- |
| 业务操作 | `BorrowCopy`，为当前读者借阅一个馆藏副本 |
| 输入 | `copyId`；身份由后端从有效会话解析 |
| 成功结果 | 借阅记录 ID、副本 ID和明确的成功状态 |
| 业务拒绝 | 副本不可借、达到借阅上限等有限结果 |
| 请求错误 | 字段格式错误、未登录、无权限、依赖不可用 |
| 数据变化 | 副本状态和借阅记录一起提交 |
| 重复提交 | 已借出副本返回确定的业务结果；需要重放同一结果时，再明确请求标识与保存规则 |
| 契约维护 | 谁维护定义、哪些前端或服务调用、改字段时如何兼容 |

### 工作约束

1. 后端必须按业务能力组织服务或模块，每个边界登记职责、所属数据、公开操作和依赖。
2. 路由集中处理协议和身份转换；业务操作组织规则与步骤；数据访问层集中处理 SQL 或 ORM 操作。
3. 身份解析与操作授权必须分别落实。后端业务层接收可信身份，并核对它对目标资源的权限。
4. 核心对象、有限状态、成功和业务拒绝必须有明确类型。内部技术异常在边界转换成稳定错误响应，日志保留排查信息。
5. 跨服务默认使用公开业务契约。表实现、SQL、内部工具及内部状态只由所属服务维护。
6. 纯业务计算应保持输入输出明确；抽取共享函数要有实际复用或可读性收益。
7. 数据库连接、HTTP 客户端等资源由基础设施统一创建和释放，业务服务使用明确的依赖。新接口应能追踪到负责的数据和验收流程。

**自己检查**：修改一条借阅规则时，需要改哪个服务？路由、业务操作和数据库方法是否各自承担明确职责？

## 四、数据库：保存事实，维护一致性

### 建议架构：PostgreSQL 单业务库＋按领域归属的表

建议以 **一个 PostgreSQL 业务库**作为业务记录的主要存储，将关系明确、需要约束和共同事务的数据放入关系表。这个起点适合账户、图书、副本、借阅等关联清楚的业务。SQL 表达查询与更新，主键、外键和约束表达允许保存的关系，事务维护需要共同完成的变化。

```text
Scala 后端：各业务服务的数据访问方法
                 ↓
          连接与事务管理
                 ↓
          PostgreSQL 业务库
  ├─ accounts 所属表：账号、角色、会话
  ├─ catalog 所属表：书目
  └─ circulation 所属表：馆藏副本、借阅记录
                 ↑
     backend/migrations/ 有序迁移
```

表按业务属主分组，项目可以使用约定的表名或独立 schema 表达归属；schema 是同一数据库内组织表的命名空间。共用业务库时，每个服务仍维护自己的写入规则，其他服务通过公开业务操作请求变更。表的访问权限和代码边界共同落实数据归属。

借书数据的主要关系可以表示为：

```text
书目 1 ── 多个馆藏副本
馆藏副本 1 ── 多条历史借阅记录
读者 1 ── 多条借阅记录
当前约束：同一副本最多有一条有效借阅
```

`catalog` 维护书目，`circulation` 维护副本和借阅；同一业务库中可使用外键维护必要关联，并登记跨模块的结构依赖。借出时，副本状态变化与新增借阅记录放在 `circulation` 的同一本地事务内。索引依据查询路径建立，例如查读者的有效借阅、查某书目的可借副本。

迁移文件是表结构演进的权威来源，表方法负责参数绑定、记录映射和读写。附件等大文件可放在项目已有文件存储中，由数据库保存其标识和业务关联；额外存储组件根据明确的数据量、查询需求和运维条件选择。独立部署服务的数据存储按服务所有权重新配置，跨服务关联通过契约维护。

### 数据归属与表结构

每类持久化事实必须有一个负责写入规则和结构演进的业务属主。借阅例子中，`catalog` 管理书名、作者等书目资料，`circulation` 管理具体馆藏副本与借阅记录，`accounts` 管理账号、角色和会话。副本通过 `bookId` 关联书目，借阅通过 `readerId` 关联读者。

| 需要定义的内容 | 具体要求 |
| --- | --- |
| 主键和身份 | 每条记录有稳定标识，说明生成方及业务含义 |
| 字段类型 | 明确字符串、整数、精确金额、时间与时区、枚举存储值 |
| 可选值 | 区分未知、未填写、零和空集合；定义允许为空的字段 |
| 约束 | 在适用位置落实非空、唯一、检查条件与关联完整性 |
| 读写路径 | 列出主要查询、排序和过滤条件，据此决定索引 |
| 归属与生命周期 | 谁创建、更新、删除；历史记录保留或失效的规则 |
| 演进方式 | 迁移文件、执行顺序、旧数据处理和验证方法 |

同一应用、同一数据库里的内部关系可使用外键。独立部署的服务保存对方标识，通过公开契约确认业务关系，避免把跨服务数据库连接作为运行前提。同一数据库实例可以承载多个服务的独立 schema 或库，访问权限与写入归属仍需分开。

### 类型与存储怎样对应

程序中的 `LoanStatus` 可存成约定好的字符串，读取时通过显式映射恢复类型。未知状态需要进入可追查的失败处理。常按日期筛选和排序的时间字段应采用适当的数据库时间类型；金额需要明确币种、精度和单位。

JSON 适合结构变化较大、通常整体读取的资料。需要频繁关联、筛选和约束的核心事实应采用可查询、可约束的结构。课程中“序列化为文本”的例子展示转换机制，具体存储方案由查询与一致性要求决定。

### 事务怎样守住业务事实

借阅一个副本需要同时改变副本可借状态和写入借阅记录。这两项事实由 `circulation` 管理，在同一数据库事务中提交。数据库访问必须使用同一个事务上下文；`IO` 的执行顺序与事务提交是两项独立要求。

读出“可借”后再单独更新，两个同时提交的请求可能都看到旧状态。实际具有并发借阅的系统，应采用数据库支持的条件更新、行锁或适合的唯一约束，并检查影响行数。选用一种能够守住当前业务不变量的方式即可。页面的禁用按钮减少重复点击，数据库操作负责最终结果。

### 工作约束

1. 每张表必须登记所属业务服务、主键、字段语义、约束和读写方法。多个服务共同写同一张业务表时，必须重新划定所有权。
2. 数据库访问集中在属主的数据访问层，使用参数绑定或等价的安全查询机制。页面、路由和无关服务通过业务入口请求操作。
3. 多次写入必须说明共同成功的范围，并将事务开始、提交、失败回滚放在明确位置。
4. 对已有的并发或重复提交场景，依据实际流程选择数据库约束和操作方式，验收结果要能复现。
5. 表结构变化必须进入有序迁移文件；已经在共享环境执行的迁移保持可追踪，后续修改使用新的迁移。
6. 迁移必须核对旧数据转换、空值、默认值和约束能否成立，并提供适合当前数据规模的恢复或修复步骤。
7. 查询返回的记录通过显式转换进入领域类型；对外响应只包含 API 契约中的字段。

**自己检查**：副本状态和借阅记录能否一起提交？旧数据如何迁移？其他服务怎样取得所需信息？

## 五、团队协作与版本管理：让改动可追踪

### 基本思路

Git 用提交保存代码历史，用分支组织并行工作。团队先约定业务词汇、接口和数据归属，再并行实现。目录、类型和服务边界一旦改变，相关说明与模板需要一起更新。

架构决策记录（ADR）保存一个重要选择的背景、决定、收益、成本和复查条件。例如“库存副本与借阅记录由同一服务维护”，记录共同事务的需要及未来何种业务变化可能触发重新评估。简单决定可以写在一页项目说明中。

### 工作约束

1. 每个任务有目标、影响范围和完成标准；并行开发前确认共享契约及各自负责的目录。
2. 修改前查看已有改动。用户正在编辑的文件和未提交内容必须保留。
3. 一次提交表达一个可理解的改动；较大改动先建立可恢复版本。推送、合并和发布按负责人授权执行。
4. 评审覆盖需求、业务边界、类型、契约、数据迁移和验证结果。跨服务改动应说明为什么需要协调变化。
5. 构建、类型检查和必要的业务流程依据实际变更执行。类型检查通过与业务验收通过分别记录。
6. 配置需求使用示例文件说明；密钥、会话令牌和真实用户资料由适当的配置与数据管理机制保存。

**自己检查**：其他人能否看懂此次变化的目的、契约影响和验证方法？

## 六、微服务：用高内聚、低耦合定义业务边界

### 模块、逻辑服务与独立部署服务

模块是代码中的职责边界。一个逻辑业务服务可以包含对象、业务操作、路由和数据访问，并与其他逻辑服务一起编译启动。独立部署的微服务有自己的进程、发布单元和数据维护责任，通过网络契约与外部协作。

课程第5讲采用逻辑微服务：服务放在不同目录，后端统一启动。这个结构适合先把业务边界落实，再根据独立发布、扩容或团队维护的实际需要决定部署方式。

| 要求 | 模块化单体中的逻辑服务 | 独立部署的微服务 |
| --- | --- | --- |
| 业务边界 | 按业务能力组织，有明确属主 | 同样按业务能力组织 |
| 调用方式 | 进程内公开接口或类型化消息 | HTTP、RPC 或已采用的消息契约 |
| 数据访问 | 所属模块封装数据；共享事务需明确记录 | 数据由所属服务独立维护，跨服务通过契约访问 |
| 发布 | 整个应用一起构建、启动和发布 | 服务可以独立构建、测试和发布 |
| 失败处理 | 函数失败、数据库失败等本地结果 | 还需处理网络超时和服务不可用 |
| 成本 | 统一运行，部署和排查较集中 | 多个运行单元，契约兼容、配置和运维成本增加 |

### 高内聚：把同一业务规则需要的内容放在一起

高内聚表示服务内部的对象、操作和数据共同完成一个清楚的业务职责。决定借阅是否成立需要副本状态、当前借阅记录和借阅规则，它们应集中在 `circulation`。改变借阅规则时，相关代码大多在这个边界内修改。

服务按业务能力命名，例如账户、书目、借阅流转。页面数量、数据库表数量、接口数量和代码行数都不能单独决定服务数量。“查询服务”“写入服务”或“数据库服务”会把同一项业务规则分散到多个地方，需要根据实际职责重新组织。

### 低耦合：让调用者只依赖稳定契约

低耦合表示服务之间通过必要、明确的契约协作。调用者知道“借阅副本”需要什么输入、会产生什么结果，内部表结构和库存实现由被调用服务维护。增加内部字段或改变算法时，调用者应能继续工作。

低耦合可以从变化成本判断：修改一个服务的内部实现，是否迫使多个服务同时修改？能否用一个契约替身验证当前服务？独立部署时，兼容的内部改动能否单独发布？频繁的双向调用、跨服务读写表、共同维护巨大的实体库、每次都协调发布，都是需要复查边界的信号。

### 服务怎样划分

围绕“用户要完成什么”识别业务能力，再列出每项能力需要维护的事实、规则和操作。把需要一起变化、一起验证或一起提交的数据先放进同一边界，然后为跨边界协作设计小而清楚的接口。

借书系统可以采用以下分工。它是适用于这个业务规模的工程方案；具体项目仍需根据自己的规则填写服务卡。

| 服务 | 职责及所属数据 | 公开能力 | 依赖范围 |
| --- | --- | --- | --- |
| `accounts` 账户 | 账号、角色、会话 | 识别身份、查询必要的账户资格 | 无需了解借阅表内部结构 |
| `catalog` 书目 | 图书标题、作者、分类等元数据 | 查询书目、维护书目 | 负责书目自身规则 |
| `circulation` 借阅流转 | 馆藏副本、借阅记录、借阅规则 | 查询可借副本、借阅、归还、查询本人借阅 | 使用可信读者身份和必要的书目契约 |

副本状态与借阅记录共同维护“一个副本最多一个有效借阅”的事实，放在同一服务内可使用本地事务。若真实业务要求将库存与借阅分别独立部署，需要先明确跨服务流程的中间状态、失败后由谁处理及用户何时看到最终结果，并评估增加的协调成本。

### 每个服务必须有一张服务卡

| 字段 | `circulation` 示例 |
| --- | --- |
| 业务能力与负责人 | 借阅和归还；负责人填写姓名或团队 |
| 负责的事实 | 副本可借状态、有效借阅和归还时间 |
| 核心不变量 | 同一副本最多一个有效借阅；归还后该借阅结束 |
| 所属数据 | `book_copies`、`loans`，以及各自迁移 |
| 公开契约 | `BorrowCopy`、`ReturnCopy`、`ListMyLoans` 等 |
| 依赖 | 可信身份、必要的书目信息；写明调用方向 |
| 事务范围 | 借阅时修改副本状态与新建记录共同提交 |
| 失败与结果 | 不可借、超过额度、网络或数据库失败的处理 |
| 部署与运行 | 当前同一应用；独立部署的需求和负责人另行填写 |
| 验收证据 | 业务流程、契约及数据一致性检查的位置与命令 |

服务卡保存在 `docs/architecture/services.md` 或对应服务文档中。新增服务、调整数据所有权或增加依赖时同步更新。

### 工作约束

1. 所有业务服务必须按高内聚、低耦合划分。一个服务围绕一组紧密相关的业务规则负责完整能力，名称表达业务含义。
2. 每个服务必须登记服务卡；评审至少检查一次真实业务流程和一次规则变更会影响哪些服务。
3. 跨服务调用必须通过公开契约。禁止直接导入其他服务的表实现、私有工具或内部状态，禁止绕过属主直接修改其数据。
4. 同一进程中的既有项目，如保留公开 Table 方法，必须登记调用方、所属数据、权限与事务责任。该兼容约定限于同一部署单元，独立部署服务使用网络契约。
5. 模块依赖应保持单向。出现双向循环时，先检查业务归属、共享概念和流程协调职责，合并紧密关联的规则或明确公开能力。
6. 服务只共享必要的契约和通用技术能力。共享领域实体、通用工具库或共同数据库模型会扩大联动修改范围，应逐项审查归属。
7. 独立部署必须有实际收益、独立启动方式、配置与验证路径。为当前同步调用设置有依据的超时和失败反馈；其他分布式机制按已确认的需求引入。
8. 跨服务流程必须说明谁发起、谁维护最终状态、如何呈现部分完成。新增协调机制前评估实际发生场景、概率依据及维护成本；推测性或极低概率场景须先取得负责人明确同意。

**自己检查**：一次借阅规则变化能否主要在一个服务内完成？其他服务依赖的是哪些公开输入和结果？

## 七、强类型：让业务含义进入程序的约束

### 类型怎样帮助发现错误

类型描述一个值代表什么、允许哪些操作和可能有哪些结果。编译器据此发现参数传错、字段缺失、状态分支遗漏等问题。静态类型检查发生在编译或构建阶段；运行时校验处理网络、文件和数据库真正送来的值。两者需要共同覆盖数据流。

“强类型”在此对应可执行的工程要求：关键概念有独立类型，有限状态明确列举，缺值和失败有明确表示，外部输入经过校验，类型检查在交付前执行。类型能够约束程序结构；库存是否仍可借、当前用户是否有权限等事实，需要在业务执行时核对。

### 关键身份与普通字符串的区别

`BookId` 表示书目，`CopyId` 表示某一本馆藏副本，`ReaderId` 表示读者。即使底层都用字符串保存，也应避免互相传入。Scala 可使用包装类型或 `opaque type`；TypeScript 可使用带品牌标记的类型或带区分字段的对象。

```scala
final case class BookId(value: String)
final case class CopyId(value: String)
final case class ReaderId(value: String)
final case class LoanId(value: String)

final case class BorrowCommand(readerId: ReaderId, copyId: CopyId)
```

编译器可以检查 `ReaderId` 与 `CopyId` 是否放在正确位置。包装类型的构造仍需根据项目规则校验字符串格式；数据库和权限检查负责确认该身份对应的事实。TypeScript 的 `type BookId = string` 只是别名，两个这样的字符串别名仍可互换。需要身份隔离时，必须采用真正可区分的类型，并把构造限制在校验入口。

金额使用明确的金额与币种类型，数量写清单位，时间写清是时间点、日期还是时长。为核心业务字段赋予含义，比给所有字符串增加相同包装更有价值。

### 有限状态与合法组合

多个布尔值可能组合出业务无意义的情况。例如 `loading=true` 同时 `success=true` 时，页面显示规则会变得含糊。判别联合用一个状态标签与该状态需要的数据绑定。

```typescript
type LoanView = { loanId: string; copyId: string };

type BorrowDisplayState =
  | { status: "idle" }
  | { status: "submitting" }
  | { status: "borrowed"; loan: LoanView }
  | { status: "failed"; message: string };

function statusText(state: BorrowDisplayState): string {
  switch (state.status) {
    case "idle": return "可以提交借阅";
    case "submitting": return "正在提交";
    case "borrowed": return `借阅成功：${state.loan.loanId}`;
    case "failed": return state.message;
    default: {
      const unreachable: never = state;
      return unreachable;
    }
  }
}
```

`borrowed` 必须附带借阅记录，其他状态只携带自身需要的信息。增加一个新状态后，穷尽检查可以提醒维护者补齐显示逻辑。Scala 可使用 `enum` 或封闭类型和模式匹配表达同样的关系。

### 缺值、业务拒绝与操作失败

| 表达方式 | 含义 | 借书例子 |
| --- | --- | --- |
| `Option[A]`／明确的可选值 | 正常结果可能缺少一个值 | 按 ID 查询后没有这本书；`Some(0)` 库存与 `None` 记录缺失各有含义 |
| `Either[BusinessError, A]`／结果联合 | 操作产生成功或可预期的业务拒绝 | 副本不可借、达到借阅上限 |
| `Try[A]` | 捕获一次可能抛异常的同步计算 | 解析数字失败；后续仍须判断是否大于零 |
| `IO[A]`／异步操作类型 | 描述需要执行的外部操作 | 查询数据库、发送请求；失败进入操作的错误处理 |
| `IO[Option[A]]` | 外部操作完成后，结果还可能缺值 | 查询执行失败与查询成功但未找到分别处理 |

实际操作可能返回 `IO[Either[BorrowError, Loan]]`：IO 管理执行和技术失败，Either 表达正常完成后的业务成功或拒绝。空值、失败和业务拒绝应有明确语义，避免用同一个 `null`、空字符串或空列表表达全部情况。

### 类型如何穿过网络和数据库

网络传输的是 JSON 等数据。TypeScript 类型断言、Scala 类型声明和前后端同名的类，都需要实际的编解码过程才能连在一起。推荐的数据路径如下：

```text
外部 JSON（未知数据）
  → 检查字段、格式、枚举与空值
  → 传输对象 DTO
  → 经过验证的领域类型
  → 业务规则与数据读写
  → 结果 DTO → JSON
```

前后端契约必须对齐字段含义、日期格式、金额单位、空值和缺字段的区别、枚举值、成功及错误结果。后端数据库记录转换到领域对象时也需要检查未知状态和不合法旧数据。接口增加可选字段通常比直接更改已有字段含义更容易兼容，具体行为仍需验证实际调用方。

### 工作约束

1. 核心身份、业务金额、数量单位和关键状态必须使用能够表达业务含义的类型；必要时通过校验构造函数建立有效值。
2. 有限状态使用枚举、封闭类型或判别联合，并处理全部分支。状态附带的数据应与状态绑定。
3. 缺值、业务拒绝、技术失败必须分别建模。解析成功后继续核对业务规则。
4. 公开接口必须声明请求、成功结果、业务拒绝和传输错误，并维护对应编解码和契约样例。
5. 外部数据以未知输入进入校验边界，校验通过后再使用。禁止用 `any`、随意断言或强制转换掩盖边界上的类型错误。
6. TypeScript 项目应开启 `strict`；现有项目逐步启用时写明当前缺口。类型检查使用真实命令运行，并验证代表性的错误输入与结果分支。
7. 领域对象、传输对象和存储记录分工清楚；简单场景可复用同一结构，出现字段含义或生命周期差异时显式转换。

**自己检查**：把读者 ID 传到副本 ID 位置能否被发现？接口返回未知状态时在哪里失败？新增状态需要修改哪些分支？

## 八、文件夹结构：让业务归属和依赖方向可见

### 项目根目录的约定

目录按业务归属和代码职责组织。每类文件有一个默认位置，同一事实有一个维护入口。项目已有成熟目录时，先给出对应关系，迁移按实际改动需要进行。

```text
project/
  AGENTS.md                     # 本项目实际约束与命令
  README.md                     # 启动、配置、验收入口
  docs/
    architecture/               # 服务卡、数据归属、依赖图、重要决定
    acceptance/                 # 关键流程与实际检查记录
  contracts/                    # 跨端／跨服务契约的权威定义（采用时建立）
  frontend/
    src/
      app/                      # 启动与路由组合
      pages/<Page>/             # 页面及页面专用组件、状态、纯函数
      apis/<domain>/            # 业务接口调用器
      objects/<domain>/         # 前端使用的业务与接口类型
      components/ui/            # 真正跨页面复用的基础组件
      system/api/               # 通用传输和错误处理
    tests/                      # 前端测试，或按项目规则与源码邻接
  backend/
    src/
      system/                   # 连接、配置、服务组合等基础设施
      services/<domain>/
        api/                    # 公开业务操作
        objects/                # 领域类型；apiTypes/ 可放专用 DTO
        routes/                 # HTTP 等传输适配
        tables/                 # 所属数据的访问实现
        utils/                  # 当前服务内部的复用函数
    migrations/                 # 当前部署单元的有序迁移
    tests/                      # 后端业务、契约和持久化检查
  scripts/                      # 开发、构建、迁移等辅助命令
  .env.example                  # 配置名称与示例值
```

这份根目录约定表达职责位置。Scala 的代码和测试落在 `src/main/scala/`、`src/test/scala/`；其他框架使用自己的标准布局，并在 `AGENTS.md` 登记映射。`contracts/` 适用于采用 OpenAPI、JSON Schema 或契约包的项目；规模较小时，可以由明确的 API 类型与编解码定义共同维护契约，并用契约样例校验两端。权威定义只选一个。

### 依赖方向的约束

| 调用方 | 允许依赖 | 必须保持的边界 |
| --- | --- | --- |
| 前端页面 | 页面内部代码、业务 API、公共 UI | 数据库访问位于后端 |
| 前端 API 调用器 | 接口类型、通用请求入口 | 页面布局和组件留在展示层 |
| 后端路由 | 业务操作、解码与身份入口 | 复杂业务规则归入所属服务 |
| 业务操作 | 领域类型、所属数据访问、明确的外部契约 | 跨服务依赖只指向公开能力 |
| 数据访问 | 所属领域类型、数据库基础设施 | 页面、路由及其他服务内部实现保持隔离 |
| 领域对象与纯函数 | 必要的基础类型和纯计算 | 网络、SQL、全局可变状态放在操作边界 |
| 共享技术库 | 通用传输、日志或配置能力 | 领域规则仍由业务服务拥有 |

顶层启动代码负责把各服务与连接等资源装配起来。通用技术库保持对具体业务无依赖，组合入口可以显式引用各服务。这样可以避免共享基础设施与业务之间出现循环依赖。

### 独立部署后怎样安排目录

如果决定独立部署，可以保留同一仓库，并在 `services/accounts/`、`services/catalog/`、`services/circulation/` 下分别放置各自的源码、依赖清单、配置示例、迁移、测试及启动说明。每个服务应有独立构建和启动入口，数据迁移由各自属主执行。契约共享只包含必要的交换格式。

目录中的 `services/` 名称只表明组织方式；独立构建、独立运行、契约调用和数据归属共同确定是否实现了微服务部署。

### 工作约束

1. 项目根目录必须登记源码、测试、迁移、配置、脚本和文档的位置。新增文件使用既定映射。
2. 后端业务代码优先进入对应领域目录，再按 API、对象、路由和数据访问分层；同一业务职责的文件应便于一起查找。
3. 前端页面专用内容留在页面目录；跨页面复用后再进入公共组件或共享能力目录。
4. `utils/` 必须有明确所属服务或页面。全局 `common/`、`shared/` 只接纳含义稳定的通用能力，并逐项说明使用方。
5. 内部文件默认私有；跨边界依赖通过公开入口。调整目录时同时核对导入路径、契约生成路径、构建和测试配置。
6. 每个文件围绕一个清楚的类型、组件或操作；每个文件夹有实际职责。拆分依据业务含义与查找成本决定。
7. 生成代码必须注明来源和重新生成命令；构建产物、报告、导出文件和对话记录分别进入产物或文档目录。源码中的生成区域通过生成器维护。
8. 服务重命名、移动数据或变更公开边界时，同步修改服务卡、契约、目录说明和验收记录。采用自动依赖检查的项目，将这些规则落实到已有工具中。

## 一个例子：借书

### 从点击到持久化

用户在书目页面选择一个可借副本，前端调用 `BorrowCopy`，提交 `copyId`。统一请求入口附加当前会话。后端路由校验输入和会话，得到可信的 `ReaderId`，构造借阅命令。

`circulation` 检查借阅资格和规则，在自己的数据库事务内确认副本状态、将其更新为借出，并新增借阅记录。需要保持一致的检查与写入由同一事务协调。事务结束后，返回明确的成功或业务拒绝；技术失败通过统一错误处理反馈。

前端把结果写入当前页面状态：成功显示借阅记录，业务拒绝显示具体原因，网络失败提供重新查询或重试入口。接口超时时，页面保留结果未知的事实；查询当前借阅记录可以帮助确定后端是否已经完成。

```text
BookList 页面
  → apis/circulation/BorrowCopy
  → circulation 路由与业务操作
  → 本地事务：book_copies + loans
  → BorrowResult
  → 页面状态与显示结果
```

### 验收与边界核对

| 场景 | 需要观察的结果 |
| --- | --- |
| 正常借阅 | 一个有效借阅；副本显示借出；前后端信息一致 |
| 副本不可借 | 明确的业务拒绝；记录保持原状 |
| 达到借阅上限 | 明确的业务拒绝；资格检查与写入之间保持业务要求的一致性 |
| 请求字段错误 | 在解码或校验边界返回请求错误 |
| 未登录或无权操作 | 后端拒绝当前操作 |
| 重复点击或实际并发借阅 | 同一副本最多一个有效借阅；记录各请求的返回结果 |
| 数据库写入失败 | 副本状态与借阅记录共同回滚，错误可追踪 |
| 网络超时 | 页面说明结果尚待确认；查询后与数据库事实一致 |

这些检查按实际采用的技术和业务流程执行。手册中的结构、代码片段和流程说明属于设计参考，具体软件项目的构建、数据库行为和部署结果需要单独验收。

## 开始一个新项目时

先建立一页项目说明，填写用户、核心流程、主要对象、业务不变量、服务卡和目录映射。每个 API 写出一组成功与失败样例，前端明确状态变化，后端明确规则与事务，数据库明确属主与迁移。

然后选择[通用 AGENTS.md 模板](模板/AGENTS.md)，或在采用 Scala + React 时选择[对应模板](模板/Scala-React-AGENTS.md)。同一项目启用一份根目录模板，填好真实路径和命令后交给 AI 执行。

可向 AI 提出以下开发要求：

> 按项目已有技术栈完成当前业务流程。先核对服务卡、数据所有权和目录映射；所有服务按高内聚、低耦合定义，跨服务使用公开契约。用强类型表达身份、状态、缺值和业务结果，并校验网络与数据库边界上的外部数据。源码、测试、迁移与文档放到约定位置。完成后给出实际运行的检查和业务验收结果；新增架构复杂度需说明具体需求和成本，推测性或极低概率场景需先取得我的明确同意。
