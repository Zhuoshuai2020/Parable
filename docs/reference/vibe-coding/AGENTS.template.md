## 技术选择与基本原则

新项目可采用以下组合；既有项目沿用已确定的技术栈，将下列职责映射到现有实现。技术调整需说明实际收益、迁移范围和维护成本。

| 部分 | 建议架构 |
| --- | --- |
| 前端 | TypeScript + React + Vite；按页面、状态、纯函数和业务 API 分工，Tailwind 作为样式选择 |
| 后端 | Scala 3 + Cats Effect + HTTP API；以模块化单体起步，按业务能力组织逻辑服务 |
| 数据库 | PostgreSQL 单业务库，表按业务域分组，由所属服务的数据方法访问；采用有序迁移和本地事务 |

1. **声明式**：先说明目标、输入输出、不变量和允许的状态，再让实现按这些约束完成操作。页面由当前状态推导，查询表达需要取得的数据。
2. **函数式**：业务计算优先采用纯函数和不可变值；相同输入得到相同结果，状态变化通过产生新值表达。
3. **副作用边界**：数据库、网络、文件等外部操作集中在明确位置。Scala 使用 `IO` 描述和组合操作，由统一运行入口执行；数据库事务另行管理提交与回滚。
4. **强类型**：核心身份、状态、缺值和业务结果进入类型定义，外部输入经过运行时校验。
5. **模块化**：按业务能力划分高内聚、低耦合的模块，相关规则和数据归属集中，跨模块通过公开契约协作。

## 工作方式

1. 先阅读相关代码、项目说明和测试，核对当前 Git 状态。保留用户已有未提交改动；禁止覆盖、重置或清除这些改动。
2. 复杂任务实施前列出目标、受影响服务、数据与契约变化、验收方式；小改动可直接实施。
3. 改动限于当前任务。扩大范围前说明实际需求和受影响文件，保留无关模块的既有实现。
4. 新增架构层次、服务或基础设施必须有明确用途。针对推测性或极低概率的竞态、安全边界增加复杂度前，必须说明具体问题、发生概率的依据、实现与维护成本，并获得项目负责人明确同意。
5. 完成后报告改动目的、文件、运行过的检查及待验证部分。验证记录必须与实际执行结果一致。

## 业务服务与高内聚低耦合

1. 服务必须围绕完整业务能力组织。紧密关联的数据、规则和状态变化由同一服务维护；服务名称表达业务职责。
2. 每个服务必须有服务卡，包含负责人、业务能力、所属数据、核心不变量、公开契约、调用依赖、事务范围、失败结果、部署方式和验收入口。新增服务或改变边界时同步更新。
3. 用真实流程和规则变更检查边界：完成一次任务应有清楚的调用路径，普通规则变更应集中在对应服务。反复跨界取数、循环依赖或多个服务同步改动同一规则时，重新评估归属与接口粒度。
4. 跨服务默认只使用公开业务 API。`tables/`、SQL、内部工具及内部状态属于服务私有实现；禁止绕过属主直接修改其数据。
5. 同一进程的既有项目保留公开 Table 方法时，在服务卡中登记调用方、数据属主、权限及事务责任。该特例限于同一部署单元；独立部署服务禁止跨服务调用 Table 方法。
6. 同一应用可包含多个逻辑服务，由一个进程启动。独立部署需要明确发布、扩容或协作收益，并提供独立构建、启动、配置、迁移和验证入口。
7. 共同维持一个业务不变量的数据应优先由同一服务管理，相关写入在本地事务中协调。跨服务流程明确发起方、最终状态属主和部分完成时的处理；新增协调机制按实际需求及授权引入。
8. 共享能力只包含确需复用的契约和通用技术机制。全局 `utils/`、`common/` 或 `shared/` 中的每项内容须有清楚职责和使用方。

借书示例：`accounts` 管理身份、角色与会话，`catalog` 管理书目，`circulation` 管理馆藏副本和借阅记录。借阅时，副本状态与借阅记录在 `circulation` 的同一本地事务中更新。其他业务按实际能力填写自己的服务划分。

## 强类型与契约

1. 核心身份使用可区分的领域类型，如 `BookId`、`CopyId`、`ReaderId`。金额包含金额单位与币种，数量和时长写清单位，时间写清日期、时间点及时区含义。
2. 有限状态使用枚举、封闭类型或判别联合，处理全部分支；状态附带的数据与该状态绑定。
3. 缺值、可预期的业务拒绝和技术失败分别表达。使用可选值和明确的成功／错误结果类型，避免让一个空值承担多个含义。
4. 请求、成功响应、业务拒绝和传输错误必须有明确契约。前后端对齐字段名、含义、格式、单位、可空性、缺省规则和枚举值。
5. 网络、文件及持久化读出的数据在边界经过运行时校验，再转换为可信领域对象。身份、权限、存在性和实时库存等业务条件在执行时检查。
6. TypeScript 项目开启 `strict`，运行真实类型检查命令。既有项目逐步启用时记录缺口和范围；禁止用 `any` 或随意类型断言掩盖边界错误。
7. 领域对象、DTO 与数据库记录具有明确转换位置。身份、日期、金额或生命周期有差异时，分别定义并检查转换。

## 前端

1. 页面列出读取信息、提交操作及对应 API；异步页面明确初始、加载、就绪、空数据、失败和提交中的呈现。
2. 核心状态具有单一归属与可追踪的更新入口；筛选、计数、分页和格式化等派生值通过计算获得。
3. 页面入口组合可见业务区域；页面专用组件、hook、状态、类型和纯函数放在页面目录。跨页面复用的基础组件进入 `components/ui/`。
4. 页面通过业务 API 调用器访问后端，调用器使用统一请求入口。组件展示、纯业务计算与网络传输各有明确位置。
5. 前端运行时校验响应，分别处理业务拒绝和技术失败；后端独立校验身份与操作权限。数据库凭证由后端持有。

## 后端与数据库

1. 路由负责解码、身份转换和响应编码；业务操作负责权限、规则、步骤与事务范围；所属数据访问层负责查询、写入和记录映射。
2. API 说明输入、输出、权限、失败及重复提交行为。外部操作集中在可定位边界，纯业务计算保持输入输出明确。
3. 每张表登记所属服务、主键、字段语义、关联、约束、更新规则及迁移位置。数据库访问集中在所属服务，页面和其他服务通过公开业务接口提交操作。
4. 修改持久化结构必须提交迁移文件，并处理旧数据兼容及必要的修复说明。手工数据库操作须有记录且符合项目授权。
5. 在适用位置落实非空、唯一、关联和状态约束。需要共同成功的写入由明确的本地事务协调，并验证失败回滚。
6. 数据库连接和外部客户端由基础设施创建和释放，业务操作使用明确依赖。

## 目录与依赖检查

- 前端页面依赖本页代码、业务 API 和公共 UI；API 调用器依赖契约类型与通用传输。
- 后端路由依赖业务操作；业务操作依赖本服务领域对象、数据访问及其他服务的公开契约。
- 数据访问依赖所属领域类型与数据库基础设施；领域对象和纯函数保持对网络、SQL、页面和全局可变状态的隔离。
- 通用基础设施保持对业务规则的独立；启动组合入口显式装配各服务。循环依赖出现时检查职责归属与调用方向。
- `utils/` 限定所属服务或页面。每个文件围绕一个清楚的类型、组件或操作，目录随真实职责建立。
- 生成代码标明来源、生成命令和独立位置；构建产物、报告、导出文件与对话记录放在已登记目录。生成区域由生成器维护。
- 服务移动或重命名时同步核对导入、契约、迁移、构建、测试和服务卡。

## 版本与验收

1. 较大改动先建立可恢复的版本或分支，提交范围对应一个可理解的任务。推送、合并和发布遵循项目负责人授权。
2. 运行与改动相关的构建、类型检查、测试或手动流程。验收覆盖实际业务风险；失败时报告原因与剩余问题。
3. 接口改动核对请求与结果样例，数据改动核对迁移与一致性，页面改动核对实际状态和操作链路。
4. 交付列出变更文件、契约与迁移影响、验证结果和需要人审的设计决定。密钥、会话令牌和真实用户数据保持在仓库外，配置要求用示例文件表达。
